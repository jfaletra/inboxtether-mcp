# v1.2 security remediation — PR #6

Date: 2026-10-17. Resolves review findings R1/R2/R3 against commit `44df8ed`. This document is not deployment, credential, sending, merge or release authorization.

## R1: historical receipt access versus current send eligibility

`SendStore.get` validates immutable record integrity without comparing it to today's SMTP settings. `eligible` performs enablement and exact-current-scope checks separately, before every durable claim and before interactive approval/review-for-send. Old pending records cannot authorize sending under changed settings; existing attempting/accepted/failed/uncertain records cannot be claimed again.

Trusted CLI status exposes historical receipts and their original scope after changes to SMTP host, port, TLS, auth username, credential reference, sending identity or client UID. Read-only status/review/reject can also load a disabled configuration. Preparation, broker service and claims still require explicit enablement. State location/migration and backup reconciliation remain operator responsibilities.

MCP status is intentionally more limited. It can inspect the minimal old status/hash only if original sending identity AND authorized MCP UID match the current owner. A changed transport still allows same-owner receipt access; a changed owner must use the trusted CLI. The IPC status schema accepts only send_id, never a trusted/owner override. Historical reads retain MIME/manifest/digest/expiry integrity checks and do not reset or purge attempts.

Regression cases cover accepted, failed, uncertain and crash-left-attempting receipts under each configuration change; disabled-config receipt reads; denied cross-owner MCP reads; denied IPC trusted flag; old-pending approval refusal after a change; and corrupted-history refusal before SMTP.

## R2: one overall monotonic IPC I/O deadline

Broker request header/body reads, response writes and error responses share one absolute five-second monotonic deadline. Each receive uses only the remaining time, so byte drips never renew the budget. Expired error paths close instead of acquiring a new timeout. Client connect/send/receive share an absolute ten-second budget. Response sendall uses the remaining total time, not per-chunk retries. There is no automatic request retry.

Local validation/data sizes and SQLite timeouts remain bounded independent safeguards; deadlines are not a hard realtime scheduler or preemption mechanism for arbitrary local code. Tests cover dripped headers and bodies, expired deadlines, incomplete headers, non-reading response peers, wall-clock changes, and a handler returning after its budget (no new success/error budget).

The Linux integration fixture additionally holds the real single broker with an authorized slow body, then checks a queued healthy status request resumes within its client budget. Kernel UID authentication and denial of MCP access to sender configuration/state remain covered. No public listener or unbounded worker pool was introduced.

## R3: sanitized isolated administrator-owned startup

The supported entrypoint is now the fixed-path `examples/secure-send/inboxtether-send` launcher, to be installed by an administrator at `/usr/local/libexec/inboxtether-send`. It executes `env -i` with exactly PATH/LC_ALL/TZ, then the fixed administrator-owned interpreter with `-I -S -B`. The systemd example and terminal documentation use this entrypoint, not raw send_assistant.py.

`send_bootstrap.py` uses isolated stdlib imports, verifies startup flags/environment and administrator-owned runtime/search-path/source ownership, then adds the validated application directory and imports application modules. User/PYTHONPATH/sitecustomize/usercustomize/venv .pth hooks are not loaded. All four source files must be administrator-owned and not group/other writable. Configuration, staging and SMTP secret remain separately sender-owned private files. Normal runtime dependencies are unchanged; the isolated sender is stdlib-only.

Before any SMTP secret is introduced, an administrator must independently establish the shell, launcher, bootstrap, interpreter/runtime and their ancestors as trusted, and the sender account must pass the isolated `--help` preflight. The bootstrap cannot retroactively defend against an already-compromised interpreter/kernel/shell, loader injection before it runs, or untrusted runtime audit/tracing hooks. No sender/root/sudo/approval terminal capability may be exposed to the model. Arbitrary raw interpreter invocations are not supported approval paths.

Tests verify dirty startup environments are rejected without running harmless environment hooks. The Linux-only fixture creates an ephemeral administrator-owned runtime/code tree: positive control proves the old invocation executes a harmless marker; the actual sanitized launcher runs successfully under hostile PYTHONPATH/PYTHONHOME/PYTHONINSPECT/SSL-keylog variables without executing environment or venv .pth hooks. Group-writable or wrong-owner application code is rejected before import. Fixtures use transient numeric UIDs and synthetic marker files, not real credentials or production accounts/services.
