# v1.2 Secure Send development review

Date: 2026-10-17. Development branch only; no deployment, credentials, live SMTP, release or merge authorized.

## Implemented boundary

- Reader stays the default. Existing v1.1 Basic/Secure Draft code and IMAP dispatch guard are unchanged.
- Disabled-by-default, Secure-only send preparation/status MCP interface; no MCP approve/send endpoint and no Basic Send fallback.
- Separately owned non-root sender, Linux kernel peer authentication in both directions, protected sender-only state/configuration/SMTP secret, administrator-controlled code/runtime, and a preparation broker systemd example restricted to Unix sockets.
- Trusted interactive terminal review binds all recipients including Bcc, From/envelope identity, fixed SMTP destination/authentication identity, exact MIME SHA-256, reply context/threading, attachment bytes/hashes, and expiry. No browser send authority is implemented.
- Atomic durable one-attempt claim, concurrency protection, retained receipts and fail-closed storage limits; expired pending records alone can be purged automatically.
- Mandatory certificate/hostname-validated TLS (implicit or non-downgradable STARTTLS), separate SMTP secret read only after claim, all recipients accepted before DATA, no protocol debug or raw server replies returned.
- Lost/unknown DATA outcomes, crashes or failed receipt persistence report uncertain, never automatically retry. No automatic Sent-folder IMAP writes or changes to existing messages.

## Validation evidence

Local Mac suite: 169 tests executed, 168 passed, one dedicated privileged Linux test skipped as intended. This includes all 128 pre-existing v1.1 tests. New coverage includes synthetic recipient/body/header validation, MIME/threading and Bcc behavior, attachment limits/export and exact hashes, credential permissions/symlinks, no pre-approval SMTP construction, wrong approval/TTY/expiry, mid-review/auth/RCPT expiry, concurrent claims, replay, process-restart attempt receipts, SMTP/auth/TLS/recipient/DATA failures, failed receipt storage, no exception leaks, frame bounds, default-mode/tool discovery and coexistence with both draft policies. Real smtplib DATA framing/dot transparency is exercised over local socketpairs with synthetic bytes.

The new `send-process-isolation` hosted CI job runs only the dedicated synthetic Linux test as root, then drops child processes to three transient numeric UIDs. It creates no system accounts or SMTP credentials. It checks legitimate prepare/status, actual Linux SO_PEERCRED rejection of a different peer in the same socket group, rejection of raw approve-send packets, and denial of MCP access to sender configuration/state. Consult the PR's current-head checks for the hosted result; local Mac results do not establish Linux isolation.

Strict dependency audits for Reader runtime, optional browser requirements and audit tooling: no known vulnerabilities found. Requirements are unchanged. Results are point-in-time advisory checks, not a guarantee of vulnerability absence. Full-history pattern scanning and manual diff review are additional detective checks, not exhaustive secret/PII detection or a penetration test.

## Residual risks and deployment gates

1. Trusted host/operator/sender account/runtime must remain outside AI control. TTY does not prove human identity; do not expose a sudo/root/sender shell tool or writable sender code to the assistant. Privilege separation must be rechecked against the actual installation.
2. Staging and review exports contain plaintext email. Require restricted backups, suitable disk encryption and deliberate receipt retention. Restoring stale state can erase single-attempt evidence: disable sending and reconcile current receipts before recovery. No automatic restore/resend procedure is supplied.
3. Standard SMTP cannot promise exactly-once or final delivery. The server/provider can rewrite headers, independently file Sent copies, or accept then bounce. Stable Message-ID is not deduplication. A fresh proposal can resend identical content only with fresh independent approval; do not do this for an uncertain attempt without reconciliation.
4. Attachments are bounded/type-checked but not malware scanned. Reviewing a digest alone is not proof a person inspected or understood bytes. Exports never execute/open content automatically.
5. The endpoint is single-mailbox/single-operator, Linux-only for send IPC. Authorized-client flooding can exhaust bounded staging; unauthorized local peers can cause bounded socket delays if administrators grant socket-group access too broadly. Multiuser ownership/routing is not implemented.
6. Browser Send approval and automatic Sent-folder synchronization remain unimplemented and require their own authorization/security review. Existing Draft portal has no send authority. Terminal is the v1.2 approval path in this draft implementation.
7. Live provider submission permissions, Mailcow SMTP behavior, actual client UX, SMTP TLS integration and final deployment isolation are unverified. No live tests have run. Credential restrictions must be verified rather than inferred from separate password issuance.
8. Deployment/credential provisioning/real sending, merging and release remain blocked pending explicit owner approval and current-head hosted checks. No production service, existing tunnel, mailbox or other repository was touched.
